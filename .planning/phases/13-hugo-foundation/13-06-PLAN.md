<deliberate_divergences>
Two adaptations needed for Hugo's routing conventions. Both produce identical URLs as Eleventy.

1. **No `permalink` front matter.** Eleventy `permalink: /404.html` and `permalink: /buscar/` map directly to Hugo's file-path conventions (`layouts/404.html` → `public/404.html`; `content/buscar/_index.md` → `public/buscar/index.html`). Omitted from the ported Hugo files.

2. **JSON serialisation of ui.levels and ui.facets.** Eleventy uses `{{ ui.levels | dump | safe }}` to serialise the dict to JSON inside an HTML attribute. Hugo equivalent is `{{ jsonify hugo.Data.ui.levels | safeHTMLAttr }}` (or just `| safeHTML`, depending on whether the output is already attribute-safe). The rendered JSON must be identical for the client-side search.js to parse it correctly. Task 2 Action verifies the rendered output equals the Eleventy reference.

Any other divergence is a rejection condition.
</deliberate_divergences>

**Note:** Hugo's top-level `layouts/404.html` receives page context differently from `_default/*`. The `.Title` is set by Hugo automatically from the page kind's title or by the site title if no page-level title exists. To get `<title>Página no encontrada | Zasqua</title>`, the cleanest approach is to set the title in baseof.html's `<title>` block alternative; OR create a `content/404.md` with front-matter title. Hugo convention is:
- `layouts/404.html` + the Hugo-generated 404 page kind sets `.Title = site.Title` unless overridden
- Setting `.Title` via `{{ $_ := .Scratch.Set "title" "..." }}` works but is hacky

**Recommended:** In `layouts/404.html`, add a `{{ define "head" }}` block that overrides the `<title>` tag — or use Hugo's `linkTitle` / `.Title` via front matter in a content file. For a simple path, create `content/404.md`:
```yaml
---
title: "Página no encontrada"
---
```
Then `.Title` resolves to "Página no encontrada" and baseof's `<title>` renders "Página no encontrada | Zasqua" as expected.

BUT: Hugo treats `content/404.md` as a regular page, not as the 404 handler. The 404 handler is strictly `layouts/404.html`. Mixing them doesn't work.

**Simplest workable approach:** In `layouts/404.html`, define a custom `<title>` via the `head` block or by overriding the baseof's title logic. Cleanest is to inline the full head section — but that breaks chassis inheritance.

**Actual chosen approach for this plan:** Use `layouts/404.html` with an explicit head block that sets the title. The `head` block exists in baseof.html (`{{ block "head" . }}{{ end }}`) but it's AFTER the `<title>` tag — so overriding won't fix the title. Override a new block or use `.Scratch`.

**Final chosen approach:** Set `.Title` via a page-level variable. The 404 template can use `{{ $title := "Página no encontrada" }}` and baseof reads `.Title`. But `.Title` is a page field, not settable in the template.

Hugo's actual mechanism: `.Params.title` or adding a front-matter title through a content file. Since 404 has no content file, we need a different approach:

**Workable:** Add a top-level block "title" in baseof.html that the 404 page overrides. Replace baseof's line:
```gotmpl
<title>{{ if .Title }}{{ .Title }} | {{ end }}{{ site.Title }}</title>
```
with:
```gotmpl
<title>{{ block "title" . }}{{ if .Title }}{{ .Title }} | {{ end }}{{ site.Title }}{{ end }}</title>
```
Then `layouts/404.html` can add:
```gotmpl
{{ define "title" }}{{ hugo.Data.ui.error404.title }} | {{ site.Title }}{{ end }}
```

**Decision for this plan:** Add the `"title"` block to baseof.html (one-line edit) and use it from layouts/404.html. This is a baseof modification BUT it's a forward-compatible addition — any page can override the title via the block. Plan 13-07 onwards will use the same pattern for pages without a front-matter title (the home page, for instance, is a section kind in Hugo and doesn't receive `.Title` the same way).

This baseof modification is a minor scope addition to this plan and must be documented in the SUMMARY.

<!-- layouts/buscar/list.html — structural port of src/buscar.njk -->

```gotmpl
{{/*
  Zasqua search page (/buscar/)

  Port of src/buscar.njk. Mounts the #search-page hook that /js/search.js
  initialises to render the client-side search UI (Pagefind-backed, with
  facet sidebar and results list). Data attributes provide the UI string
  translations so JS can render faceted labels in Spanish.

  The inline IIFE sends a server-side analytics beacon when the user
  performs a search (q query param). This is preserved byte-for-byte from
  the Eleventy source — the Cloudflare Worker endpoint receives the
  query string and logs it for the analytics dashboard.

  Version: v1.0.0
*/}}
{{ define "title" }}{{ .Title }} | {{ site.Title }}{{ end }}
{{ define "main" }}
<div class="container font-sans">
  <div id="search-page"
       data-level-labels='{{ jsonify hugo.Data.ui.levels | safeHTMLAttr }}'
       data-facet-labels='{{ jsonify hugo.Data.ui.facets | safeHTMLAttr }}'>
  </div>
</div>

<script src="/js/search.js"></script>
<script>
(function() {
  var q = new URLSearchParams(location.search).get('q');
  if (q) navigator.sendBeacon('https://neogranadina-dashboard.neogranadina.workers.dev/api/beacon/search?q=' + encodeURIComponent(q));
})();
</script>
{{ end }}
{{/* Version: v1.0.0 */}}
```

Note: if `| safeHTMLAttr` doesn't produce byte-equivalent output to Eleventy's `| dump | safe` (e.g. if Hugo escapes characters that Nunjucks doesn't), fall back to `| safeHTML` or compute the full attribute via `printf` + safeHTMLAttr:
```gotmpl
{{ printf `data-level-labels='%s'` (jsonify hugo.Data.ui.levels) | safeHTMLAttr }}
```
Task 2 verification compares the rendered attribute value to the reference.
