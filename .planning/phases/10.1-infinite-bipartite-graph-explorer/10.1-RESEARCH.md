## Summary

Phase 10.1 replaces the curated 100-node static graph on `/entidades/` with a fully interactive bipartite graph explorer where users follow entity→document→entity chains indefinitely. The codebase already contains the complete interaction model in `src/js/entity.js` — node rendering, tooltip patterns, expand-on-click, hover highlighting, role filters, shard caching, and Pagefind integration are all proven and reusable. The main work is: (1) reimplementing these patterns at the page level with viewport-filling layout, (2) adding bidirectional graph↔sidebar sync, (3) adding hop-distance pruning and virtual overflow nodes, and (4) making data pipeline changes to support role-based Pagefind filtering.

The most technically novel aspects are the bidirectional sync (D-13 through D-17) and the hop-distance node management (D-36 through D-38). Everything else directly adapts from entity.js. The document→entity reverse lookup is the one open architectural choice — `desc-entity-lookup.json` (5.7 MB, pre-built) is the strongest option: no async Pagefind search needed per document node, and no extra build step required.

**Primary recommendation:** Adapt `entity.js` patterns directly — do not reinvent. The simulation configuration, tooltip structure, shard caching, and Pagefind integration all transfer without modification. Build the new `InfiniteBipartiteExplorer` class as a fresh file, wire it to the refactored `EntitiesExplorer` class, and redesign `entidades.njk` as the viewport-filling container.

### Pattern 3: Document→Entity Reverse Lookup (D-22 — Claude's discretion)

**What:** To determine whether a document node is expandable (has entity connections beyond those already in the graph), the new explorer needs to look up `refCode → [entityCodes]`.

**Recommendation: use `desc-entity-lookup.json`** rather than Pagefind async search.

Rationale:
1. `desc-entity-lookup.json` already exists at 5.7 MB [VERIFIED: data/desc-entity-lookup.json]
2. It is generated by `precompute-links.js` which is staying [VERIFIED: scripts/precompute-links.js]
3. A single `fetch('/data/desc-entity-lookup.json')` loads all reverse lookups into a Map — then all subsequent lookups are synchronous
4. In `entity.js`, `checkExpandable()` fires Pagefind search once per document node in an async loop (lines 582–606). With 30 document nodes on initial load, that is 30 sequential Pagefind queries just for the expandable pre-check. desc-entity-lookup eliminates this entirely.
5. 5.7 MB is acceptable for a dedicated explorer page (the user explicitly chose this page for graph exploration)

**Loading strategy:**
```javascript
// Load desc-entity-lookup once on class init, store as Map
async function loadDescLookup() {
  const resp = await fetch('/data/desc-entity-lookup.json');
  const obj = await resp.json();
  // Convert to Map for O(1) lookup
  return new Map(Object.entries(obj));
  // obj keys: reference_codes, values: array of entity_codes
}
```

### Pattern 4: Hop-Distance Pruning (D-36 through D-38)

**What:** Track how many hops each node is from the current focal entity. When refocusing, prune nodes > 3 hops. Pruned entity shards stay in `shardCache` for seamless reload.

**Algorithm:**
```javascript
function computeHopDistances(focalId) {
  const hopMap = new Map();
  hopMap.set(focalId, 0);
  const queue = [focalId];
  while (queue.length) {
    const curr = queue.shift();
    const currHop = hopMap.get(curr);
    const neighbours = nodeNeighbours.get(curr) || new Set();
    for (const nb of neighbours) {
      if (!hopMap.has(nb)) {
        hopMap.set(nb, currHop + 1);
        queue.push(nb);
      }
    }
  }
  return hopMap;
}

function pruneDistantNodes(focalId, maxHops = 3) {
  const hopMap = computeHopDistances(focalId);
  const toRemove = new Set();
  graphNodes.forEach((_, id) => {
    if (!hopMap.has(id) || hopMap.get(id) > maxHops) toRemove.add(id);
  });
  // Remove from graphNodes and graphEdges
  toRemove.forEach(id => graphNodes.delete(id));
  graphEdges = graphEdges.filter(e => !toRemove.has(e.source) && !toRemove.has(e.target));
  // Incrementally update graphData without rebuilding
  const current = graphInstance.graphData();
  graphInstance.graphData({
    nodes: current.nodes.filter(n => !toRemove.has(n.id)),
    links: current.links.filter(l => {
      const s = typeof l.source === 'object' ? l.source.id : l.source;
      const t = typeof l.target === 'object' ? l.target.id : l.target;
      return !toRemove.has(s) && !toRemove.has(t);
    })
  });
  graphInstance.d3ReheatSimulation();  // D-42
}
```

**Note:** After `graphInstance.graphData({ nodes, links })`, force-graph replaces its internal node objects with the new array. The `source` and `target` in links become references to node objects — check for this when filtering. The pattern above handles both string IDs and object references. [VERIFIED: entity.js lines 718–723 handles this same issue]

### Anti-Patterns to Avoid

- **Auto-zoom on engine stop:** `onEngineStop(zoomToFit)` causes the jarring jump users reported. Do not add it. Use a single `zoomToFit(0, 30)` after 300ms on initial load only. [VERIFIED: entity.js line 424 does this; D-40 removes it for the new explorer]
- **Full graphData rebuild on node addition:** Always use incremental `graphData({ nodes: old.concat(newNodes), links: old.concat(newLinks) })` + `d3ReheatSimulation()`. Full rebuild resets positions and causes layout jumps. [VERIFIED: entity.js lines 716–760]
- **Pagefind for expandable pre-check:** Using Pagefind to check each document node's expandability at startup is too slow for 30 concurrent async queries. Use desc-entity-lookup.json instead.
- **Loading the full `entity_links.json` (82 MB) client-side:** Never. Always use per-entity shards (median ~0.3 KB).
- **Rebuilding adjacency after every node add:** Rebuild adjacency once per batch, not per node.
- **Removing `cooldownTime` without setting `alphaMin`:** If you remove `cooldownTime`, also ensure `alphaMin` is low enough that the simulation does settle rather than running forever at full CPU. The default `alphaMin` (0.001) is fine.

## Common Pitfalls

### Pitfall 1: `source`/`target` become object references after `graphData()`

**What goes wrong:** After you call `graphInstance.graphData({ nodes, links })`, force-graph mutates the link objects — `link.source` and `link.target` become references to node objects (not strings). Code that filters edges by string ID will break silently.

**Why it happens:** force-graph calls `d3.forceSimulation` internally, which resolves string IDs to node object references.

**How to avoid:** Always resolve with: `const s = typeof l.source === 'object' ? l.source.id : l.source;` [VERIFIED: entity.js lines 719–723 does exactly this]

**Warning signs:** Edge deduplication logic stops working; `edgeKeys.has(s + '→' + t)` returns false for edges already in the graph.

### Pitfall 2: Viewport-filling layout conflicts with `page-content` min-height

**What goes wrong:** The base layout sets `<main class="page-content">` with `min-height: calc(100vh - var(--header-height) - 260px)`. If the explorer app container tries to use `height: 100%`, it will resolve against `min-height` rather than the viewport.

**Why it happens:** `min-height` on a parent does not establish a fixed height that `height: 100%` can resolve against. Children of flex or grid parents with explicit height work; children of min-height parents don't.

**How to avoid:** Two options:
1. Add `height: 100%` to `html, body, main.page-content` — global change, may affect other pages.
2. Use `height: calc(100vh - var(--header-height) - BREADCRUMB_HEIGHT)` directly on the explorer container — explicit, self-contained. Measure the breadcrumb height (typically 40–44px based on existing `.breadcrumb` CSS).

Recommended: Option 2 — explicit calculation, no global side effects. [ASSUMED — exact breadcrumb height not measured; verify in browser]

### Pitfall 3: Entity node name/type unavailable when expanding via reverse lookup

**What goes wrong:** `desc-entity-lookup.json` gives you entity codes for a document, but not entity names or types. To show new entity nodes with labels and colours, you need name + type.

**Why it happens:** entity.js solves this by fetching `/entidad/{code}/` HTML pages (lines 669–684) — but that fires one HTTP request per new entity.

**How to avoid:** Two options:
1. Fetch entity pages individually (existing pattern) — fine for small expansions (cap at 15 entities per D-34), adds latency.
2. Use `entity-index.json` (19 MB pre-built) — single fetch gives all entity metadata. Too large for reliable client-side load.
3. Load Pagefind entities index and query by code — add entity metadata to Pagefind index (already there: `entity_type`, `linked_count`, `date_earliest`) and query via `pagefind.search(code, { filters: { entity_code: code } })`. However, Pagefind does not support exact-match filtering on a unique ID field by design.

**Recommended approach:** Keep the existing entity page fetch pattern (option 1) but batch requests with `Promise.all` for the capped 15 entities. At 15 parallel requests of ~10–20 KB each, latency is acceptable. [VERIFIED: entity.js lines 669–684]

### Pitfall 4: Pagefind WASM blocks the main thread on first load

**What goes wrong:** The first `pagefind.init()` call downloads and initialises the Pagefind WASM bundle (~250 KB). During this time, the UI freezes briefly.

**Why it happens:** WASM compilation is synchronous and blocks rendering.

**How to avoid:** Initialise Pagefind entities index asynchronously in the background while the graph is rendering its initial state. The sidebar search is not needed until the user types. Add `await new Promise(r => requestAnimationFrame(() => requestAnimationFrame(r)))` before the WASM init to let the graph paint first. [VERIFIED: entity-explorer.js line 136 uses this exact pattern]

### Pitfall 5: The `cooldownTime` default is 15000ms — not "infinite"

**What goes wrong:** If `cooldownTime` is not explicitly set, force-graph defaults to 15000ms, after which the simulation stops. Adding nodes after the simulation cools causes `d3ReheatSimulation()` to work, but the initial state will have the graph freeze after 15 seconds.

**How to avoid:** For a continuous "Obsidian-like" simulation, set `.cooldownTime(Infinity)`. But this means the simulation runs forever — CPU drain. Better: set a long cooldown (e.g., 60000ms) and rely on `d3ReheatSimulation()` for node additions. Or set `alphaTarget(0.05)` which keeps the simulation gently alive indefinitely with minimal CPU use. [ASSUMED — force-graph `alphaTarget` API not verified against current CDN version; verify in browser]

### Pitfall 6: `entidades.njk` permalink and passthrough copies

**What goes wrong:** The current template is at `src/explorar/entidades.njk` with `permalink: /entidades/`. If the new template also loads `force-graph` via CDN in `{% block head %}`, the CDN script will be in `<head>`, not `<body>` — force-graph must be available before the inline `<script>` at the bottom.

**How to avoid:** Keep the `{% block head %}` CDN script pattern from `entidades.njk`. [VERIFIED: current entidades.njk line 8]

### Pitfall 7: role filter on entity pages — `data-pagefind-filter` must be per-value

**What goes wrong:** To add role as a Pagefind filter (D-54), each role value that an entity appears in must be its own `<span data-pagefind-filter="role">value</span>`. The roles are not stored in entity pages — they are in entity-link shards. This means the build step must compute per-entity roles.

**How to avoid:** Extend `precompute-links.js` to output per-entity role lists (already grouping by entity_code; roles are present on each link object). Add role arrays to `entity-index.json` or pass them to the `entidad.njk` template via a computed global data file. Then in `entidad.njk`, loop over the entity's roles and emit one filter span per role — same pattern as `year` filter (lines 18–20 of `entidad.njk`).

**Implementation path:** The entity template already does `{% for y in ent.date_earliest | yearRange(ent.date_latest) %}`. A similar `{% for r in ent.roles %}` loop works if `ent.roles` is populated at build time. Requires: (a) precompute-links.js adds roles to each entity record, and (b) the entity template receives them. [VERIFIED: entidad.njk lines 18–20 for the year pattern]
