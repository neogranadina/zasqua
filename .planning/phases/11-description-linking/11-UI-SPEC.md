**Link states (from `.detail-field a` and `.detail-field a:hover` — `input.css` lines 2385–2392):**
- Resting: `color: stone-900 (#26.8% oklch)`, underline with `text-decoration-color: stone-300`, `text-underline-offset: 2px`
- Hover: `color: var(--color-burgundy-light)` (`#B14D66`)

Plain `<a href="...">` inside `.detail-field` inherits the correct rule automatically.

**Entity type colour distinction:** CONTEXT.md leaves this to Claude's discretion. Decision: do not add entity-type colour to links. Reasons: (1) the role label already provides semantic differentiation, (2) adding burgundy vs. periwinkle link colours would conflict with the existing link colour rule and require JS class injection, (3) CONTEXT.md is explicit that plain anchor links are preferred.

## Copywriting Contract

Source: CONTEXT.md D-06 through D-08; `src/_data/ui.js` roles object and section headers.

| Element | Copy |
|---------|------|
| Primary CTA | Not applicable — this phase adds no buttons or CTAs; entity/place names are the navigational affordance |
| Section heading (entities) | `ui.description.entitiesHeader` (Spanish, defined in `ui.js` — executor must confirm exact string) |
| Section heading (places) | `ui.description.placesHeader` (Spanish, defined in `ui.js` — executor must confirm exact string) |
| Entity link + role pattern | `{display_name}` — *{Rol1, Rol2}* (link followed by em dash and italic comma-separated Spanish role labels) |
| Place link pattern | `{display_name}` (plain link, no role label — per D-08) |
| Empty state (entities section) | Section is absent entirely — no section rendered when `desc._entity_links` is empty (per D-03) |
| Empty state (places section) | Section is absent entirely — no section rendered when `desc._place_links` is empty (per D-03) |
| Error state | Not applicable — build-time data; if lookup fails, section is absent (same as empty state) |
| Destructive confirmation | Not applicable — no destructive actions in this phase |

**Role label source:** Spanish role strings come from `ui.roles` in `src/_data/ui.js`. The current vocabulary covers 5 keys (`creator`, `contributor`, `publisher`, `subject`, `mentioned`). The backend `entity_links.json` contains 29 distinct role values — 24 are unmapped. The executor MUST extend `ui.roles` with Spanish translations for all 29 roles before the template task runs. This is a human approval gate: the Spanish archival/legal terms must be reviewed by the user before committing.

**Role label fallback (for roles not yet in `ui.roles`):** If a role key is not found in `ui.roles`, do not display any role label for that entity — omit silently rather than showing the raw English key. This preserves a clean Spanish-only UI while the vocabulary is being extended.

## Interaction Contract

This phase has no JavaScript interactions. All links are standard `<a href>` elements generated at build time.

### Entity link rendering

```
{entity.display_name} — {Rol español 1, Rol español 2}
```

Rendered as:
```html
<div class="detail-field">
  <a href="/entidad/{entity.code}/">{entity.display_name}</a>
  {% if entity has roles %}
  — <em class="text-stone-400">{Rol1, Rol2}</em>
  {% endif %}
</div>
```

- Link URL: `/entidad/{entity.code}/` — entity codes are URL-safe (`ne-XXXXX`), no filter needed
- Role labels: comma-separated, wrapped in `<em class="text-stone-400">`, preceded by ` — ` (space–em dash–space)
- One `<div class="detail-field">` per entity
- All entities shown regardless of count (up to 210) — no truncation in this phase (per RESEARCH.md Pitfall 5 decision)

### Place link rendering

```html
<div class="detail-field">
  <a href="/lugar/{place.display_name | safeSlug}/">{place.display_name}</a>
</div>
```

- URL: `/lugar/{display_name | safeSlug}/` — safeSlug strips `?` and `#` only; spaces and accented chars are preserved
- No role label, no type label (per D-08)
- One `<div class="detail-field">` per place

### Section visibility rules

- Render `Personas y entidades` section only when `desc._entity_links.length > 0`
- Render `Lugares` section only when `desc._place_links.length > 0`
- Do not fall back to plain text for names without a matching code (per D-03) — the enriched lookup contains only resolved names

### Pagefind filter spans (must be preserved)

`description.njk` lines 35–40 use `desc._entity_codes` and `desc._place_codes` (string arrays) for `data-pagefind-filter` spans. These must remain as string arrays alongside the new enriched object arrays. The data loader must derive them: `desc._entity_codes = desc._entity_links.map(e => e.code)`.
