<decisions>
## Implementation Decisions

### Pagefind Strategy
- **D-01:** Entity and place pages are **excluded from Pagefind** (`data-pagefind-ignore` on the page body or excluded from the Pagefind indexing step entirely). Site-wide search (`/buscar/`) stays description-only. Explorer pages (`/explorar/`) use their own in-memory JSON filtering
- **D-02:** Clean separation: `/buscar/` searches descriptions via Pagefind; `/explorar/entidades/` and `/explorar/lugares/` search entities and places via pre-built JSON index files

### Explorer Search Data
- **D-03:** Pre-built JSON metadata files (`entity-index.json`, `place-index.json`) are generated at build time. Explorer pages load these once on init and filter in-memory with vanilla JS
- **D-04:** `entity-index.json` is a single file (not sharded). At ~5-8 MB uncompressed (~1-2 MB gzipped), it's acceptable for a discovery page. Cloudflare edge caches after first request
- **D-05:** `place-index.json` is a single file. At ~300 KB it's lightweight

### Entity Index Fields
- **D-06:** `entity-index.json` includes per record: `entity_code`, `display_name`, `sort_name`, `entity_type`, `date_earliest`, `date_latest`, `primary_function`, `linked_description_count`

### Place Index Fields
- **D-07:** `place-index.json` includes per record: `place_code`, `display_name`, `place_type`, `lat`, `lon`, `has_wikidata` (boolean), `has_whg` (boolean), `has_hgis` (boolean), `linked_description_count`

### Linked Descriptions in Explorers
- **D-08:** Explorer results show metadata and description count. When the user clicks/expands an entity or place, the per-entity or per-place JSON shard is fetched on demand (e.g. `data/entity-links/{code}.json`). Same shards the detail pages use — no duplicate data

### Claude's Discretion
- Whether the index files are generated by the same `precompute-links.js` script or a separate script — whatever keeps the code clear
- Directory structure for index files (`data/indexes/` vs alongside link shards) — whatever fits the build pipeline
- DEV_MODE handling for entity/place builds — limit count for fast local iteration

</decisions>

## Existing Code Insights

### Reusable Assets
- `src/_data/descriptions.js` — Pattern for data loading: read JSON, build lookup maps, precompute relationships. Entity/place data loaders should follow the same CommonJS `module.exports = async function()` pattern
- `build.sh` — Local build pipeline. Needs entity/place data download and pre-compute steps added
- `.github/workflows/deploy.yml` — CI pipeline. Needs parallel Eleventy build step and merge
- `scripts/upload-to-r2.py` — Upload script works as-is; just needs to upload the merged `_site/`

### Established Patterns
- Data pipeline: Django backend -> B2 upload -> build-time download -> Eleventy -> Pagefind -> R2 deploy
- `DEV_MODE` environment variable limits data for fast local builds (currently 100 descriptions)
- CommonJS modules for all Node.js data files (`require`, `module.exports`)
- Progress logging via Eleventy transform (every 5,000 pages)
- Passthrough copy for static JSON files served client-side (`data/children/`)

### Integration Points
- `data/` directory — New files: `entities.json`, `places.json`, `entity_links.json`, `place_links.json` (downloaded from B2)
- `data/entity-links/` and `data/place-links/` — Pre-computed per-entity and per-place JSON shards (generated by pre-compute script)
- `data/entity-index.json` and `data/place-index.json` — Pre-built metadata index files for explorer search
- `eleventy.config.js` — Passthrough copy needed for link shards and index files
- Backend export (`zasqua-backend-dev`) — Must provide `entity_links.json` and `place_links.json` in addition to existing `entities.json` and `places.json`
