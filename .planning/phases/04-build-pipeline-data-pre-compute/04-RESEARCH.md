**D-01:** Entity and place pages are excluded from Pagefind (`data-pagefind-ignore` on the page body or excluded from the Pagefind indexing step entirely). Site-wide search (`/buscar/`) stays description-only. Explorer pages (`/explorar/`) use their own in-memory JSON filtering.

## Summary

Phase 4 delivers the data pipeline and build architecture — nothing visible to users, but everything the subsequent template phases depend on. There are four distinct deliverables: (1) pre-computed per-entity and per-place JSON link shards, (2) pre-computed entity and place metadata index files for explorer search, (3) a pre-computed entity co-occurrence JSON file, and (4) a CI pipeline that builds all pages in parallel without OOM or timeout.

The most important finding from reading the backend export command directly is that **`entity_links.json` and `place_links.json` do not yet exist in the export** — they must be added to `export_frontend_data.py` in the backend (`zasqua-backend-dev`) as a prerequisite for this phase. The existing export produces entities.json and places.json but has no link export phases. This is the first task of this phase and gates everything else.

A second critical finding is the field name mismatch: places.json exports `latitude` and `longitude` (matching the Django model field names), not `lat`/`lon` as assumed in earlier research. The pre-compute script and index file generation must account for this. D-07 specifies `lat`/`lon` in `place-index.json` — the pre-compute script must rename these fields when writing the index.

The build architecture research recommends starting with a single Eleventy build to validate correctness, then switching to parallel builds only if the combined build exceeds ~25 minutes. The existing build uses `--max-old-space-size=6144` in CI. The entity/place build should get its own Node process with a separate heap allocation.

**Primary recommendation:** Add entity_links and place_links export to the backend first. Then build precompute-links.js, wire up build.sh and deploy.yml, profile combined build time, and add the parallel build architecture only if needed.

### Pattern 2: precompute-links.js

**What:** Node.js script that reads entity_links.json and place_links.json from `data/`, writes per-entity and per-place JSON shards to `data/entity-links/{entity_code}.json` and `data/place-links/{place_code}.json`, and also writes `data/entity-index.json` and `data/place-index.json` for explorer search.

**When to use:** Runs before any Eleventy build step. Must complete before Eleventy processes entity/place templates.

**Pattern (following descriptions.js CommonJS style):**
```javascript
// scripts/precompute-links.js
'use strict';
const fs = require('fs');
const path = require('path');

const DATA_DIR = process.env.DATA_DIR || path.join(__dirname, '..', 'data');
const DEV_MODE = process.env.DEV_MODE === 'true';
const DEV_LIMIT = parseInt(process.env.DEV_LIMIT || '500', 10);

async function main() {
  console.log('[precompute] Reading entity_links.json...');
  const entityLinks = JSON.parse(fs.readFileSync(path.join(DATA_DIR, 'entity_links.json'), 'utf8'));
  console.log(`[precompute] ${entityLinks.length.toLocaleString()} entity-description links`);

  // Group by entity_code
  const byEntity = new Map();
  for (const link of entityLinks) {
    if (!byEntity.has(link.entity_code)) byEntity.set(link.entity_code, []);
    byEntity.get(link.entity_code).push({
      reference_code: link.reference_code,
      title: link.title,
      date_expression: link.date_expression,
      repository_code: link.repository_code,
      role: link.role,
    });
  }

  // Write entity-links shards
  const shardsDir = path.join(DATA_DIR, 'entity-links');
  fs.mkdirSync(shardsDir, { recursive: true });
  let count = 0;
  for (const [code, links] of byEntity) {
    fs.writeFileSync(path.join(shardsDir, `${code}.json`), JSON.stringify(links));
    count++;
    if (count % 10000 === 0) console.log(`[precompute] ${count.toLocaleString()} entity shards written`);
  }
  console.log(`[precompute] Wrote ${count.toLocaleString()} entity-links shards`);

  // Build entity-index.json (D-06 fields + linked_description_count)
  const entities = JSON.parse(fs.readFileSync(path.join(DATA_DIR, 'entities.json'), 'utf8'));
  const entityIndex = entities.map(e => ({
    entity_code: e.entity_code,
    display_name: e.display_name,
    sort_name: e.sort_name,
    entity_type: e.entity_type,
    date_earliest: e.date_earliest,
    date_latest: e.date_latest,
    primary_function: e.primary_function,
    linked_description_count: (byEntity.get(e.entity_code) || []).length,
  }));
  fs.writeFileSync(path.join(DATA_DIR, 'entity-index.json'), JSON.stringify(entityIndex));
  console.log(`[precompute] Wrote entity-index.json (${entityIndex.length.toLocaleString()} records)`);

  // Repeat for places
  // ... (same pattern with place_links.json → data/place-links/{place_code}.json)
  // D-07: lat/lon fields renamed from latitude/longitude in places.json
}

main().catch(err => { console.error(err); process.exit(1); });
```

**DEV_MODE handling:** In DEV_MODE, limit shards written to DEV_LIMIT entities/places so the precompute step is fast during development.

### Pattern 5: precompute-cooccurrence.js

**What:** Reads entity_links.json, groups links by reference_code to find entities co-occurring in the same description, emits weighted edges, filters by configurable minimum weight.

**Data scale:** 308K entity-description links, 92K entities. Group by reference_code first (one pass), then for each description with ≥2 entities, emit all entity-pair edges. Accumulate edge weights, then filter.

**Example:**
```javascript
// scripts/precompute-cooccurrence.js
const MIN_WEIGHT = parseInt(process.env.COOCCURRENCE_MIN_WEIGHT || '3', 10);

// Group by description
const byDesc = new Map();
for (const link of entityLinks) {
  if (!byDesc.has(link.reference_code)) byDesc.set(link.reference_code, []);
  byDesc.get(link.reference_code).push(link.entity_code);
}

// Emit edges
const edgeWeights = new Map();
for (const [refCode, codes] of byDesc) {
  if (codes.length < 2) continue;
  const unique = [...new Set(codes)].sort();
  for (let i = 0; i < unique.length; i++) {
    for (let j = i + 1; j < unique.length; j++) {
      const key = `${unique[i]}|${unique[j]}`;
      edgeWeights.set(key, (edgeWeights.get(key) || 0) + 1);
    }
  }
}

// Filter by minimum weight
const edges = [];
for (const [key, weight] of edgeWeights) {
  if (weight >= MIN_WEIGHT) {
    const [source, target] = key.split('|');
    edges.push({ source, target, weight });
  }
}

// Build node list (only entities that appear in filtered edges)
const nodeSet = new Set();
for (const e of edges) { nodeSet.add(e.source); nodeSet.add(e.target); }
```

**Output format (data/entity-cooccurrence.json):**
```json
{
  "min_weight": 3,
  "generated_at": "2026-03-26T00:00:00Z",
  "nodes": [
    { "id": "PE001234", "label": "García, Juan", "type": "persona", "count": 45 }
  ],
  "edges": [
    { "source": "PE001234", "target": "PE005678", "weight": 7 }
  ]
}
```

**Scale note:** At threshold ≥3, the graph is expected to be much smaller than the full 92K entities. The exact size is unknown until the script runs against real data — this is explicitly flagged in the CONTEXT.md `<specifics>` section. Threshold is configurable via `COOCCURRENCE_MIN_WEIGHT` env var.

### Anti-Patterns to Avoid

- **Anti-pattern: Loading entity_links.json (308K records) as a global Eleventy data file.** This would hold ~30 MB in Node heap per template pass. Use the pre-compute script + per-entity shards instead.
- **Anti-pattern: Using `--incremental` for data-driven pagination builds.** Eleventy's incremental mode does not track data file changes — entity pages would silently remain stale after a data update. Always full rebuild.
- **Anti-pattern: Loading entities.json in the description build.** The description build does not need entity data; loading it wastes heap.
- **Anti-pattern: Running Pagefind before merging parallel build outputs.** Always merge first, index once.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| File I/O for 92K JSON shards | Custom streaming write logic | Plain `fs.writeFileSync` in a loop | Node.js handles 92K small file writes fine; the shard files are tiny (~1-5 KB each) |
| Co-occurrence edge accumulation | Custom graph library at build time | Plain Map-based edge counting | No graph library needed for the pre-compute step — it's just pair counting |
| B2 download | Custom HTTP client | Existing `b2 file download` CLI calls in build.sh | Already working; just add new download commands |
| Parallel process management in CI | Custom job orchestrator | GitHub Actions `jobs.<id>.needs` or bash `wait $PID1 $PID2` | Standard bash process management is sufficient |

**Key insight:** This phase is fundamentally file I/O and Map iteration — the complexity is in correctness (right field names, right shard keys) not in the algorithms. Resist the urge to add libraries.

## Common Pitfalls

### Pitfall 1: Field name mismatch — latitude/longitude vs lat/lon

**What goes wrong:** places.json exports `latitude` and `longitude` (matching the Django model). D-07 specifies `lat` and `lon` in `place-index.json`. If precompute-links.js copies fields verbatim, place-index.json will have `latitude`/`longitude` while the explorer JS expects `lat`/`lon`.

**Why it happens:** Research documents used `lat`/`lon` shorthand; the backend export uses full field names.

**How to avoid:** In precompute-links.js, explicitly map `p.latitude → lat` and `p.longitude → lon` when building place-index.json records. Verify with `console.log(Object.keys(places[0]))` at the start of the script.

**Warning signs:** place-index.json records have `null` for lat/lon even for places with coordinates.

### Pitfall 2: place_code is nullable in the DB

**What goes wrong:** The `place_code` field on the Place model has `blank=True, null=True`. Some places may not have a place_code. Using place_code as the shard filename will fail for these records.

**Why it happens:** place_code is auto-generated but only if not set. Older place records may lack it.

**How to avoid:** In the backend export, verify all place records have a place_code before adding to place_links.json. Alternatively, fall back to using the `id` field as the shard key and cross-reference in place-index.json. Log a warning for any place with null place_code.

**Warning signs:** KeyError or undefined filename when writing place shards.

### Pitfall 3: entity_links.json and place_links.json are not yet exported

**What goes wrong:** The backend export command (`export_frontend_data.py`) does not have export phases for entity_links.json or place_links.json. Running precompute-links.js will fail immediately with "file not found".

**Why it happens:** These export phases were planned but not yet implemented in the backend.

**How to avoid:** The first task of this phase must be to add these export phases to the backend. This requires working in `zasqua-backend-dev`, running the Django export command, and uploading the new files to B2 before any frontend pre-compute work can proceed.

**Warning signs:** `ENOENT: no such file or directory: data/entity_links.json`.

### Pitfall 4: Memory pressure from loading entities.json in the description build

**What goes wrong:** If entities.js is activated (loads entities.json) but both description and entity pages are in the same Eleventy build, the description build unnecessarily holds 29.9 MB of entity data in heap.

**Why it happens:** Eleventy loads all `src/_data/*.js` files for every build — there is no per-template conditional loading.

**How to avoid:** If using Option A (single build), entities.js and places.js loading the full arrays is unavoidable. Acceptable trade-off since the description build already handles larger data. If using Option B (parallel builds), entities.js is only loaded in the entities build, not the description build — structure the second config to use a different `_data` directory.

**Warning signs:** Description build OOM in CI when entities.js has been activated.

### Pitfall 5: Co-occurrence script produces enormous output without threshold

**What goes wrong:** Without a minimum weight threshold, the co-occurrence graph could have millions of edges (all pairs of co-occurring entities, including those sharing only one document). Writing this to JSON would produce a file too large to serve.

**Why it happens:** At 308K entity-description links with ~3 entities per description on average, even a threshold of 1 produces a very large graph.

**How to avoid:** Default threshold to 3 in the script. Make it configurable via env var `COOCCURRENCE_MIN_WEIGHT`. Log node and edge counts before writing. If counts seem large (>50K edges), raise the threshold before committing the output file.

**Warning signs:** entity-cooccurrence.json is larger than 50 MB.

### Pitfall 6: GitHub Actions timeout with combined build

**What goes wrong:** The combined build (descriptions + entity/place pages sequentially) could exceed 30 minutes, putting pressure on the 60-minute CI timeout when Pagefind indexing and R2 upload are added.

**Why it happens:** Each entity/place page adds to Eleventy's template processing time. 92K entity pages + 8K place pages = 100K additional pages on top of 106K descriptions.

**How to avoid:** Profile a DEV_LIMIT build first. Estimate total time by extrapolation before committing to a build architecture. If a single sequential build would exceed 30 minutes, implement parallel builds.

**Warning signs:** Build step in CI takes more than 28 minutes — leaves only 32 minutes for Pagefind + upload.

```python
# Add to export_frontend_data.py handle() method, after Phase 7 (places):

self.log_phase('Phase 8: Writing entity_links.json')

from catalog.models import DescriptionEntity
entity_link_rows = list(
    DescriptionEntity.objects
    .select_related('description', 'entity')
    .values(
        'entity__entity_code',
        'description__reference_code',
        'description__title',
        'description__date_expression',
        'description__repository__code',
        'role',
    )
)

entity_link_records = []
for link in entity_link_rows:
    entity_link_records.append({
        'entity_code': link['entity__entity_code'],
        'reference_code': link['description__reference_code'],
        'title': link['description__title'],
        'date_expression': link['description__date_expression'] or '',
        'repository_code': link['description__repository__code'],
        'role': link['role'],
    })

entity_links_path = os.path.join(output_dir, 'entity_links.json')
with open(entity_links_path, 'w', encoding='utf-8') as f:
    json.dump(entity_link_records, f, ensure_ascii=False)

size_mb = os.path.getsize(entity_links_path) / 1024 / 1024
self.log(f'  Wrote {len(entity_link_records):,} entity links ({size_mb:.1f} MB)')
self.log_elapsed()
```

## Open Questions

1. **entity_links.json and place_links.json export scale**
   - What we know: 308K entity-description links and 85K place-description links (from PROJECT.md)
   - What's unclear: Exact file size of the exports; whether the Django query needs any filtering (e.g. exclude needs_review=True links)
   - Recommendation: Export all links without filtering initially; profile file sizes before deciding whether to exclude review-flagged links

2. **place_code completeness**
   - What we know: place_code is nullable in the DB model; auto-generated on save
   - What's unclear: Whether any production Place records have null place_code
   - Recommendation: Add an assertion or warning in precompute-links.js that logs places with null place_code; decide on fallback (use `id` or skip)

3. **Co-occurrence output size at threshold 3**
   - What we know: 308K links, expected to produce many pairs; threshold 3 filters significantly
   - What's unclear: Actual node/edge count at threshold 3 until script runs against real data
   - Recommendation: Log node/edge counts before writing. If >50K edges, document for Phase 9 threshold tuning.

4. **Single vs parallel build timing**
   - What we know: Current description build takes ~14 minutes; entity/place build expected similar
   - What's unclear: Exact combined build time until profiled
   - Recommendation: Build and profile with a DEV_LIMIT run first; decide on parallel architecture based on measured time
